# Agent Note: Differential desktop hot updates

Status: implemented

English | [中文](2026-08-16-differential-desktop-hot-updates.zh.md)

## Problem

The self-contained Windows NSIS package is large because it includes the application runtime, but a hot update that changes a few UI strings must not redownload that package. Treating the first-install package as the update asset made the update larger than necessary and could exceed GitHub release asset limits.

## Decision

First installation remains a speed-first NSIS package using `compression: "store"`. Hot updates use a signed NSIS delta executable generated by `scripts/build-desktop-delta.mjs`. The delta carries only the changed files under `resources/app.asar.unpacked` and applies a same-length version replacement in `resources/app.asar`; it does not contain the full ASAR or the full application directory. The existing updater can launch the delta through its verified NSIS installer path, so the updater-enabled 1.0.0 client can consume the 1.0.1 patch.

The release manifest points to the delta asset, not the first-install package. A delta is accepted only after it has been applied to a fresh previous-version installation and that installed executable returns HTTP 200, exposes the required boot entries, serves the changed plugin behavior, and has no plugin-load error.

## Alternatives considered

- **Publish the full NSIS installer as the hot-update asset.** Rejected: it redownloads unchanged runtime files, violates the requested file-level update behavior, and can exceed GitHub's release asset limit.
- **Publish a full application ZIP.** Rejected: it has the same unnecessary payload and needs a separate replacement protocol, while the existing updater already launches verified NSIS executables.
- **Replace plugins in the running process.** Rejected: it complicates rollback and can leave a mixed-version runtime; the signed restart-time file patch keeps replacement atomic at the process boundary.

## Consequences

- Text-only releases can produce KB-scale update assets while the first-install package remains optimized for installation time.
- The delta must name the exact packaged files and must be tested from the immediately previous installed version; testing a fresh new-version install is insufficient.
- Changes to files inside `app.asar` need an explicit delta operation. The current helper only supports the desktop package version marker plus unpacked changed files, so other ASAR changes require extending and testing the helper before release.
