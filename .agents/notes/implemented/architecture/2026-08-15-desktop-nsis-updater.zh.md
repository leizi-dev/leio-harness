# Agent Note：桌面端签名 NSIS 更新

状态：已实现

[English](2026-08-15-desktop-nsis-updater.md) | 中文

## 问题

桌面端需要一个与公开 Leio 仓库一起维护的、带签名且在重启时替换文件的更新通道，同时保持首次安装包以安装速度优先。

## 决策

桌面端只保留一个正式发布目标：Windows x64 NSIS 安装包。打包后的 Electron 主进程在启动后检查 GitHub 稳定通道清单，并通过范围受限的 preload bridge 暴露检查、下载和安装动作。Web 设置 bundle 只有在发现该 bridge 时才贡献更新行，因此浏览器部署仍保持原有界面且无法访问桌面进程能力。

清单会先被规范化，再使用内置 Ed25519 公钥验证。下载文件写入按版本隔离的用户数据目录，校验清单声明的文件大小和 SHA-256 摘要后，才在当前应用退出后启动独立安装程序。

## 备选方案

没有选择 `electron-updater`，因为本仓库已经拥有 GitHub 发布布局，而更新器必须只接受仓库自己的签名清单。拒绝进程内替换 ASAR 或 Portable，是因为正在运行的 Electron 进程无法安全替换自己的资源，且之前的 Portable 构建不适合作为可靠发布目标。

## 影响

现有的 `1.0.0` 安装必须先通过普通安装包人工获得一次带更新器的版本。后续版本必须使用更高的 SemVer，并同时发布安装包、清单和独立签名。Ed25519 密钥保护更新通道；Windows Authenticode 签名仍是独立的信任和 SmartScreen 问题。

安装包使用 ASAR 和 `store` 压缩优先保证安装速度。只解包产品、供应商、共享的 `zod` 和原生运行时依赖；完整解包依赖树曾产生 27,341 个安装文件，安装验收后予以否决。优化后的构建解包 7,141 个文件，在本机安装实测耗时 187.5 秒。

## 验证

发布流程记录在 [`updates/README.md`](../../../../updates/README.md)。桌面发布 skill 要求全新 NSIS 安装、安装后的应用返回 HTTP 200、boot entry 非空、核心 client modules 和 layout 存在、不出现插件加载失败、标题正确并且可以优雅关闭，之后才能交付产物。
